## Findings

**No vulnerabilities in this review met the skill's reporting threshold of confidence
0.7 or higher.** This is stated plainly rather than padded with a speculative entry, as
Step 7 requires.

One pattern was traced to a concrete, demonstrable effect and would otherwise have been
reported as a Finding. It is recorded under **Notes** below because fixing it would
contradict the project's explicitly stated design decision, which is the test Step 5
sets for that distinction. It is not dismissed as a false positive, and the technical
mechanism is preserved in full in Note 1.

The following patterns were examined and excluded, each for a reason given in Step 5's
exclusion list or because the traced effect was not exploitable:

- **Reentrancy.** `fission`, `fusion`, and both transmutations carry `nonReentrant`.
  `adjustPeg()` does not and is reachable from a base-token transfer hook inside
  `fissionAux`, but `alphaBefore` and `reserveRatio` are both snapshotted before the
  transfer, so the mint stays proportional and no profit path exists.
  `IOracle.readValue` is declared `view`, so both reader call sites compile to
  `STATICCALL` — a malicious oracle cannot re-enter the reactor even from the non-view
  `_readAndCacheBasePrice`.
- **Factory reentrancy.** `StableCoinFactory.deployReactor` is unguarded and makes an
  external token call, but its balance-delta accounting
  (`factoryBalanceBefore` → `amountIn`) survives a nested deployment, the
  `forceApprove` is fully consumed by `initialFission`, and registry writes happen only
  after it returns.
- **Access control.** `Tokeon.mint`/`burn` are `onlyOwner` with the reactor as owner,
  and the reactor has no code path that transfers or renounces that ownership.
  `initialFission` is factory-only and one-time. `setBetaParams` is treasury-only. No
  use of `tx.origin`. No proxy or `delegatecall` anywhere in the codebase.
- **Rounding and precision.** `fusion`'s `nBurn`/`pBurn` both floor, so a redeemer burns
  marginally less than pro-rata, but the `nBurn == 0 || pBurn == 0` guard bounds the
  per-call gain below one wei of each tranche — far under gas cost. This is a missing
  best practice with no concrete exploit path (Step 5 exclusion).
- **Arithmetic.** Solidity `^0.8.20` with no `unchecked` blocks. `_protonPriceInBase`'s
  `equity = normalizedReserve − liabilities` cannot underflow, because `neutronPrice` is
  `min(target, R/N)` and therefore `liabilities <= R` in both branches.
  `_grossBaseToInt` bounds the `int256` cast.
- **Permanent DoS via `alpha`.** `adjustPeg()` is permissionless and scales `alpha` by
  `0.99` whenever the ratio is below critical. Were `alpha` to reach exactly zero,
  `_reserveRatioWad` would return `type(uint256).max` and every operation including
  `fusion` would revert permanently, with the UP branch unable to recover. This was the
  strongest DoS candidate and does not occur: `Math.mulDiv(N, alpha, WAD)` floors to
  zero first, which returns `type(uint256).max` and flips `adjustPeg` to the UP branch
  before `alpha` can reach zero. The descent self-arrests at `alpha = 1`. The condition
  therefore does not meet the "permanently lock funds" bar the Step 5 DoS exclusion
  carves out.
- **Oracle zero-price cache poisoning.** `adjustPeg` and both transmutations return
  normally rather than reverting at a zero price, so a cached zero would persist and
  leave no usable fallback. The `if (basePrice != 0)` guard at `StableCoin.sol:257-259`
  prevents this, and `testCachedPriceSurvivesTemporaryZeroOraclePrice` covers it.
- **Token standards.** `SafeERC20` is used throughout, so missing-return-value tokens
  are handled. `fission` measures the actual received amount, so fee-on-transfer tokens
  are handled on deposit. `fusion` transfers `net = m − fee` and a fee-on-transfer token
  would short the redeemer, but the shortfall falls on that redeemer rather than the
  protocol, and such tokens are outside the 0–18-decimal standard-ERC-20 model the
  README documents.
- **Secrets and configuration.** No hardcoded keys, credentials, or signing material.
  `script/Deploy.s.sol` reads `PRIVATE_KEY` from the environment via `vm.envUint`, which
  is the expected Foundry pattern.
- **Dependency and remapping integrity.** The context-scoped remapping
  `lib/OrbOracle-Solidity/:lib/openzeppelin-contracts/=lib/OrbOracle-Solidity/lib/openzeppelin-contracts/`
  isolates the Orb submodule's OpenZeppelin from Gluon's. No shadowing or
  wrong-contract import was identified. Dependency *age* alone is excluded by Step 5.

## Notes

### Note 1: Transmutation prices tranches at an unvalidated, indefinitely frozen oracle price — `src/StableCoin.sol:516` and `src/StableCoin.sol:564`

- Category: design-tradeoff / accepted-risk
- Observation: Both transmutation paths obtain `basePrice` from
  `_readAndCacheBasePrice()` (`transmuteProtonToNeutron` at line 516,
  `transmuteNeutronToProton` at line 564) and derive the Proton↔Neutron exchange rate
  from it through `_pricesInBase`. Nothing in the protocol checks the age of that price.
  `IOracle` declares `lastUpdated()` (`src/interfaces/IOracle.sol:13`) and both the
  Chainlink adapter and the integrated Orb oracle implement it, but no Gluon contract
  calls it — a repository-wide search finds it only in test assertions. Since PR #43,
  `_readAndCacheBasePrice()` additionally returns `lastSuccessfulBasePrice` whenever
  `ORACLE.readValue()` reverts (`StableCoin.sol:261-262`), so the price driving the
  exchange rate can be frozen for an unbounded period while the market moves.

  Transmutation is value-conserving only at the price used, so a party who knows the
  true price can convert between tranches at the wrong rate and take value from the
  other tranche's holders. The effect is a zero-sum redistribution of claims on the
  reserve, not protocol insolvency — fission and fusion are unaffected, because the
  oracle price cancels out of both the mint and the burn formula.

  The precondition is reachable by two independent routes. The integrated Orb
  `Oracle.readValue()` carries a `notBlacklisted` modifier that checks `msg.sender`, and
  the caller is the reactor, so blacklisting the reactor freezes its cache; Orb's
  blacklist condition is `diff * DENOMINATOR > q * undecided`, and `q` is a free
  constructor parameter, so at `q = 0` a single vote suffices. Separately, an oracle
  that simply stops updating leaves a stale value with no fallback involved at all. The
  repository's own `testTransmutationUsesCachedPriceWhenOrbBlacklistsReactor`
  (`test/OrbOracleIntegration.t.sol`) constructs exactly this state — it asserts
  `orbOracle.readValue()` returns `2e18` while `reactor.getBasePriceInPeggedAsset()`
  returns `1e18`, then executes both transmutations against the frozen price. That test
  asserts the balance mechanics and makes no assertion about economic fairness.

  Neither existing guard prevents the mispricing. `_requireOperatingRange` is evaluated
  using the same stale price and so cannot detect the divergence. The beta fee does not
  bound it either: the defaults are `betaPhi0 = betaPhi1 = 0`, and the `betaPhi1` term
  is a function of `decayedVolumeBase`, which starts at zero — so the volume component
  is necessarily zero on the first transmutation regardless of how `phi1` is configured.

- Rationale: Fixing this would contradict the project's stated design. Asked directly
  whether a freshness bound using `IOracle.lastUpdated()` should be added, the Gluon
  maintainer Bruno (@Zahnentferner, listed as a maintainer in `MAINTAINERS.md`) replied:
  "It is a design decision for Gluon not to block operations when oracle prices are
  'stale'. Blocking operations also has negative consequences and we consider these
  consequences worse than the consequences of allowing operations with 'stale' oracle
  prices."

  That decision is consistent with the repository's own written guidance.
  `CONTRIBUTING.md`, under "Timestamp and Staleness," states that "Consumers are
  responsible for deciding whether an oracle value is too old for their use case unless
  the project architecture explicitly defines otherwise," and directs contributors not
  to "add independent staleness-revert behavior inside an oracle integration without
  prior discussion because it can change integration semantics." It is also consistent
  with the mechanism PR #43 introduced, whose stated purpose is to keep the reserve
  reachable when the oracle reverts rather than locking user funds behind an unreadable
  price.

  This Note records an accepted tradeoff, not a withdrawn observation. The behavior
  described above remains technically possible in the reviewed code; the maintainers
  have consciously chosen protocol liveness over blocking on staleness. Operators
  deploying a reactor against an Orb instance should be aware that the `q` parameter of
  that Orb instance governs how easily a third party can freeze the reactor's price, and
  that this is a deployment-time choice rather than something the reactor can enforce.

## Limitations

This review does not replace a full manual audit or a penetration test.

**Standing limitations**

- This review does not replace a full manual audit or a penetration test.
- This is static analysis of source text. Nothing was executed, fuzzed, or traced at
  runtime, so timing-dependent, load-dependent, or infrastructure-dependent issues
  cannot be confirmed here.
- Confidence scores are the reviewing model's own self-assessment, not a calibrated
  statistical probability.
- Absence of a reported finding does not mean the code is secure. Safety guardrails
  built into some models can cause a real vulnerability to be softened, generalized, or
  left out rather than reported in exploit-level detail, and training-data bias can make
  some vulnerability classes easier for a model to recognize than others. Treat this
  report as a floor on what a full audit would find, not a ceiling.
- Findings reflect the reviewing model's training data cutoff. A vulnerability tied to a
  very recently disclosed CVE or library advisory may not be recognized as such.
